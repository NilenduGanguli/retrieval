## 1. Fleet-wide embedding model → `gte-large-en-v1.5` (1024-D)

**Commit:** `feat: fleet-wide gte-large-en-v1.5 @1024 …`
**Full detail:** [`docs/EMBEDDING_MODEL.md`](EMBEDDING_MODEL.md) — read that first; this is
just the orientation.

### The problem it fixes

`retrieval` and [`document-enrichment-services`](https://github.com/NilenduGanguli/document-enrichment-services)
(DES) read and write the **same** `chunk_embeddings.embedding` pgvector column. The
production (Stellar) path already used `gte-large-en-v1.5` (1024-D), but the **local /
Vertex fallback still used `text-embedding-005` (768-D)** — so local and prod were
producing vectors that cannot coexist in one column. Two models in one index does not
error; it silently returns wrong neighbours. That is the bug this closes.

### What changed here (config + docs only — no runtime code was rewritten)

| File | Change |
|---|---|
| `backend/app/config.py` | New authoritative `embedding_model` = `gte-large-en-v1.5`, `embedding_dim` = `1024`. New `embedding_base_url` / `embedding_api_key` / `embedding_api_style` (`openai`\|`tei`) for serving gte locally. `vertex_embedding_model` kept but marked **LEGACY / fallback-only** (768-D, not fleet-compatible) — deliberately not deleted, so anyone mid-migration is not broken. |
| `ingest_remote/app/config.py` | Same block, adapted to the WEGA/Vertex provider split. |
| `ingest_remote/app/bootstrap.py` | `emb_dim = settings.embedding_dim` (was hard-coded `768`). Feeds both `CHUNK_EMBEDDINGS_DDL` and `ENSURE_EMBEDDING_COL_SQL`, so both now render `vector(1024)`. |
| `docs/EMBEDDING_MODEL.md` | New. Model rationale, the 768→1024 migration SQL, and how to serve gte locally. |

### ⚠️ What is NOT done — the actual remaining work

**No existing rows were re-embedded.** This change makes new writes 1024-D and makes a
stale column fail loudly; it does not migrate data. Before this is live end to end:

1. **Decide the cutover for each database.** A pgvector column has a fixed dimension: a
   `vector(768)` column rejects every 1024-D insert. Either
   - dev: drop and recreate the table (fastest), or
   - real data: re-embed every row with gte, then
     `DROP INDEX …; ALTER TABLE … ALTER COLUMN embedding TYPE vector(1024);` and **rebuild
     the HNSW index** (it is not valid across a dimension change).
   The SQL sketch is in `docs/EMBEDDING_MODEL.md`.
2. **Stand up a gte endpoint for non-Stellar environments.** Set `embedding_base_url` to an
   OpenAI-compatible or TEI server. Verified facts from 2026-08-05:
   - Running it in-process via `sentence-transformers` works **only** with
     `sentence-transformers==3.0.1`, `transformers==4.44.2`, `einops`,
     `trust_remote_code=True`, and `device='cpu'`. Apple MPS crashes this model, and newer
     `transformers` breaks the custom RoPE code that ships in the model repo.
   - HuggingFace **TEI publishes linux/amd64 only** — on Apple Silicon it runs under
     emulation.
3. **Confirm the dense-retrieval path reads `embedding_model`,** not a hard-coded name, in
   `backend/app/pipeline/dense.py` and any query-embedding call site. This change added the
   authoritative settings; it did not audit every consumer.

### How DES relates

DES writes chunks into this same schema and is already fully on gte @1024 (it ships an
embedding-provider matrix `http | local | vertex | stub`, and a startup guard that returns
`503` from `/api/readyz` when the stored column dimension disagrees with the configured
one, with the remediation in the message). Mirroring that guard here would be a cheap win.

## 2. Performance tuning (pre-existing WIP, committed as-is)

**Commit:** `perf: size the connection pool, executor and worker count …`

This work was **already uncommitted in the working tree** before the embedding change; it
was not authored as part of it. It was reviewed for coherence and syntax and committed
unchanged so it would not be lost. It is a themed set:

- `backend/app/db.py` — asyncpg pool sizing via `PG_POOL_MIN` / `PG_POOL_MAX` (default
  5/30). **Note:** sizing is *per worker* — total connections = workers × `max_size`, so
  check it against Postgres `max_connections` before raising worker count.
- `backend/app/main.py` — default `ThreadPoolExecutor` widened to `APP_EXECUTOR_WORKERS`
  (default 64), because every sync LLM/embedding/OCR call goes through
  `run_in_executor(None, …)` and the stdlib default (~6 threads) throttles concurrency.
  Also prefers `ORJSONResponse` when `orjson` is importable.
- `entrypoint.sh` — worker count defaults to `nproc × 2` (cgroup-aware via
  `os.sched_getaffinity`), opportunistic `uvloop` / `httptools`, access log off unless
  `APP_ACCESS_LOG=true`.

**Not benchmarked.** The defaults are reasoned, not measured — validate under real load
before treating them as tuned, especially `APP_EXECUTOR_WORKERS=64` and the pool maximum
against your Postgres connection limit.
